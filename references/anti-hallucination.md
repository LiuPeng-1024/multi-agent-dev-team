# 防幻觉约束 (Anti-Hallucination)

> AI 会**自信地产生幻觉**。"验证而非信任"是底线,但不够。本文件是系统化的约束,所有角色都要遵守。

## 七大约束

### 1. 工具锚定 (Tool Grounding)
任何关于代码、文件、依赖、API 的断言,必须基于**实际读取的内容**,不能凭记忆或常识推断。
- ✅ "读取了 `src/auth.py:42`,这里缺少空值检查"
- ❌ "auth 模块应该有登录逻辑"(没读就说)
- **强制**:对代码下结论前,必须先用 Read/Grep 看到实际内容。

### 2. 事实/推测分离
明确区分两类陈述,推测要标注置信度:
- **事实**:"来自文件X/工具Y的输出" → 直接陈述
- **推测**:"我猜这里是这么设计的" → 必须标注 `[推测]`,并说明依据和不确定度
- 不要把推测伪装成事实。

### 3. 可证伪声明 (Falsifiable Claims)
所有"完成了/修复了/正确"的声明,必须附带**可验证的证据**:
- 说"bug修复了" → 附:复现步骤 + 修复后测试通过的输出
- 说"这个改动没破坏其他" → 附:全量测试结果
- 说"性能达标" → 附:具体的基准数字
- 性能/容量/平衡类结论(如"够快/够长/够稳")尤其要**实测数字,不能靠推理**——实测中"survive 到 30 回合"的推理被 sim 证伪(实际 ~15),推理式性能声称是高频幻觉
- **没有证据的声明,等于没声明。**

### 4. 关键决策双重确认 (Dual Confirmation)
高风险决策不能单一智能体拍板,需两个独立智能体确认:
- 架构方向变更(架构师提 → 审查者核)
- 安全相关改动(开发者实现 → 独立安全角色核)
- 删除/重写已有逻辑
- 依据:单一视角容易盲点,交叉验证降低系统性错误。

### 5. 引用追溯 (Source Tracing)
任何结论能追溯到源头:
- 引用代码 → 标 `文件:行号`
- 引用决策 → 标文档区块(如"ADR-07")
- 引用验证 → 标测试名/输出
- 不能追溯的结论,要标注"无法验证来源"。

### 6. 不确定就说不确定
遇到不确定,必须二选一,**不能编造**:
- 声明"不确定,需要查" → 然后去查(读文件/跑命令)
- 或声明"这超出我的可靠判断,需人介入"
- 这是 prompt 层强约束。宁可坦白不确定,也不要编一个听起来合理的答案。
- 编造的代价远高于坦白——它会污染下游所有角色。

### 7. 小步快验 (Small Steps, Fast Verification)
不一次性产出大量代码再验证,而是:
- 小步产出 → 立即验证 → 确认对 → 再下一步
- 这减少幻觉累积:越早发现错,代价越小
- 对应到内层循环:开发者每写一个可测单元就交验,不要憋一大坨。

## 补注1:测试基础设施的假绿风险(实测补强)

> 实测发现:测试本身可能"假绿"——非因代码对,而是测试基础设施有竞态/共享态。假绿比"没测试"更危险:它给"完成"声明提供**虚假证据**(违反约束3)。防幻觉不能只查"有没有测试",还要查"测试信号可不可信"。

**典型:并行测试共享磁盘文件竞态**
- 多测试文件并行跑(`node --test`、pytest-xdist 等)若共享一个磁盘状态文件(快照/缓存/DB),A 的 setup/teardown 可能在 B 的 写→读 之间删掉该文件 → B 读取返回空 → 断言偶发失败(flaky)。
- 实例:案例A（某回合制 web 游戏） persist 测试偶红(~1/10),根因非代码逻辑,而是并行文件共享 `.state.snap.json` 的 rmSync 竞态。
- 修法:每测试进程用**唯一隔离路径**(如 pid 后缀),或测试串行,或内存态 mock 掉磁盘。
- 规律标签:"flaky 先查基础设施竞态,别只盯代码逻辑" → 进幻觉日志必查项。

**其他假绿源**:并发未串行化的共享可变态(HTTP 边界外的全局态)、mock 与真实行为漂移、测试依赖执行顺序。凡"偶红"一律当假绿嫌疑,查基础设施而非归咎运气。

## 补注2:验证工具自身也要抽样复核(实测补强)

> 实测发现(案例A（某回合制 web 游戏） Phase2):`guard-check.py` 的 `extract_hallucination_tags` 取 `cells[-1]` 抓的是"关联角色/任务"列而非"规律标签"列——**防幻觉工具自身有 bug**,回流的是错的必查项。平时不跑真项目看不出来;在真项目跑 guard-check 时看到"必查项"是角色名才暴露。

**约束**:防幻觉/验证工具(脚本/oracle/CI)自身的输出**不能假设无 bug**。其输出也要在真实项目抽样复核——至少第一次接入时人眼扫一遍输出是否合理(如必查项是不是真的规律标签、而非某列数据)。

- 这不编号进"七大约束"(避免触发"7→8"的全 skill 措辞同步),作为补注
- 适用:guard-check.py 的标签回流、coverage/mutation 工具的数字、任何"工具说 X"的断言
- 与约束3(可证伪声明)同源:工具的输出也是一种"声明",需要(抽样)验证而非全信

## 补注3:未知日志 + 落地后深审(诚实自检闭环,实测补强)

> 约束#6 说"不确定就说不确定",但只停在"当下坦白"。问题是:角色完成任务时往往**不知道自己不知道**——把假设当事实、把推理当验证、把"没查"当"没问题"。需要一道**完成时自检**:做完后回头看,哪些是我没把握的?记下来,等交付后专门深审,而不是当场卡住(当场卡住永远发不了版)。

### 完成时自检(尤其 04 开发者 / 03 架构师)
每个任务做完、声明完成前,角色自问四连:
- 我有哪些**假设**当事实用了?(没验证就依赖的)
- 我有哪些**推理**当验证用了?(推了但没实测)
- 我有哪些**没查**当"没问题"了?(没读/没跑就说"应该没事")
- 这块的边界/副作用/并发/性能,我有**把握**吗?没把握的标出来

把自检出的不确定项记入**区块14(未知/盲区日志)**——不是卡住不让过,是诚实标注"这块我没把握,shipped with risk",留待落地后深审。**尤其 04/03**:开发者最容易把"没查当没事",架构师最容易把"假设当事实"。

### 为什么不 gate(区别于幻觉日志)
- **区块11(幻觉日志)**记"自信地说了错的"——被抓到的,已造成问题,**gate**(规律标签回流必查项,guard-check 卡)
- **区块14(未知日志)**记"诚实承认不确定的"——没造成问题(还没炸),**不 gate**——若每个不确定都卡,永远发不了版。它是**知识债**,不是缺陷
- **边界(升级路径)**:区块14 的条目若后来被证明是"明知不确定却声称完成" → 升级为幻觉,移入区块11(明知不确定≠诚实坦白,是隐瞒=幻觉)

### 落地后深审(消费区块14)
框架/任务落地(过退出门禁交付)后,**专门开一轮深审**:编排者读区块14 全部未知项,逐条:
- 能补验证的 → 派 04/05 补实测(把"推理当验证"的还回去)
- 是假设且未验证 → 派人/补实验确认
- 是架构盲区 → 03 重新评估该决策
- 不需深究的 → 标记关闭

> 这轮深审不卡交付(交付已过门禁5),是**复盘提能**——把"这次不知道的"变成"下次知道的",系统性降低盲区。类比区块6(技术债):6=结构债 03 驱动还,14=知识债 落地后深审还。

### 与已有约束的关系
- **约束#6(不确定就说不确定)**:本补注是它的**完成时强化版**——不只当下坦白,还完成时回扫+持久化到区块14
- **约束#3(可证伪声明)**:补注3 与它互补——约束#3 要求"声明带证据",补注3 说"没证据的标风险记入14,不假装有证据"。允许先 ship(标注风险)落地后补,而非当场堵死——**务实**(若每个不确定都当场堵,没有项目能交付)
- **区块11(幻觉日志)**:本补注是它的**前置预防层**——诚实自检能减少"假设当事实"演变成真幻觉(被交叉核对抓到)

## 审查者的额外职责

审查者除了审 diff,还要审**产出过程的质量**——检查上面7条有没有被违反。例如:开发者说"修复了"但没附证据,审查者应打回要求补证据。这是防幻觉的第二道闸。

## 强制执行:借力 verification-before-completion

约束 #3(可证伪声明)的硬性执行依赖 `verification-before-completion` skill。它的铁律:

> **NO COMPLETION CLAIMS WITHOUT FRESH VERIFICATION EVIDENCE**

意思是:任何角色宣布"完成/修复/通过"前,**必须在本轮先跑过验证命令并附上输出**。没跑过就不能声称。审查者据此核对:开发者有没有真跑、证据是否新鲜。这是防幻觉约束从"原则"落到"机制"的关键。

## 发现与纠正机制(怎么抓幻觉、怎么防复发)

上面7条是"怎么少产生幻觉"。但幻觉不可能消灭,所以还需要"**产生了怎么被发现、被纠正**"。详见 `cross-verification.md`,核心四机制:

1. **全量交叉核对**:每个"完成"声明由**非作者角色独立复现证据**(不信声明,只信复现)。复现失败=幻觉被抓。
2. **幻觉日志**(事实来源文档区块11):每次幻觉记 声明/真相/怎么发现/纠正/规律标签。知识管理者维护,定期找规律。
3. **质疑前移**:审查者/红队默认不信任任何声明,对每个"完成/通过/符合"追问"证据/复现/来源"三连。质疑不只验收时,开发阶段就对复杂逻辑攻。
4. **可执行守卫断言**:编排者每轮必填 checklist(所有完成声明有非作者复现证据?测试是本轮新鲜跑的?)。幻觉日志的规律标签回流为永久必查项。

> **闭环价值**:幻觉一旦被发现,它的类型就永久进入必查清单。系统越来越难犯同类幻觉——不是每次靠人盯,而是系统自我加固。
