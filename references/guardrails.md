# 失控护栏 (Guardrails)

> 多智能体系统最大的工程风险是**失控**:死循环、活锁、预算爆炸、在死胡同里打转。本文件定义具体数值和机制,防止这些。
>
> ⚠️ **本文件的默认值是 P2(独立生成)基线,被任务画像覆盖**。同一触发(如超时)在不同任务画像下走**不同 handler**——见 `exception-handling.md` 的画像→(限制+handler)总表。本文件管"流程控制"(循环/预算/升级阶梯一律撞墙→叫人);`exception-handling.md` 管"按场景的失败 handler"(可恢复错误有自愈路径)。两者互补。

## 默认数值(P2 基线,可按项目调,被画像覆盖)

> 下表是 **P2(独立生成)画像**的基线值。派任务前编排者先按 `exception-handling.md` 的 4 问决策树定画像,套对应画像的数值(handler 见画像总表)。"被画像覆盖"列指本基线在该画像下被什么值替换。

| 护栏 | P2 基线 | 触发动作 | 被画像覆盖(见 exception-handling.md) |
|------|--------|---------|----------------------------------|
| 内层循环最大轮数 | 5 轮 | 升级(见下) | P1=1-2轮 / P4=2-3轮 / P5=宽 |
| 无进展判定 | 连续 2 轮无净进展 | 触发"卡住"处理 | 画像无关(通用) |
| 单任务步数预算 | 50 步 | 强制停下复盘 | P3=100步(集成型) |
| 总迭代预算 | 项目级设定 | 超限强制 review | 画像无关(项目级) |
| 等待超时 | 某角色等依赖 > 设定步数 | 检查依赖是否死锁 | 画像无关(通用) |
| 子代理超时 | 见下（按画像，墙钟基准） | 进展检测优先于墙钟（见下） | P1=60s / P2=15-30min / P4=按操作耗时 / P5=按预算 |
| 并发度上限 | (本表无,见 exception-handling.md handler 6) | 超限排队 | 默认 N=4 |

## 失败升级阶梯(核心机制)

**不是无限重试,而是分层升级。** 当内层循环撞到上限或无进展时,按此阶梯升级,每级换思路:

```
第1-2轮: 原角色原地重试(开发者自己修)
   ↓ 仍失败
第3-4轮: 换角度——审查者诊断根因,开发者按诊断改
   ↓ 仍失败
第5轮(撞上限): 换角色/换实现方式——架构师介入重新设计
   ↓ 仍失败
重新分解: 编排者把任务拆得更细,或拆成更小可验单元
   ↓ 仍失败
叫人: 标记为"需人介入",说明卡在哪、试过什么
```

> 关键:**到顶一定是人,不是无限循环。** 系统永远有一条出路叫"停下来叫人"。
>
> ⚠️ **"撞上限"的轮数随画像变**:上表"第5轮"是 P2 基线。P1 查证任务 1-2 轮就该升级(别在 trivial 上烧预算);P4 副作用型 2-3 轮即停(副作用异常直接 checkpoint+叫人,见 `exception-handling.md` handler 1)。升级阶梯**结构**通用,撞限**时机**按画像。

## 无进展检测 (Progress Detection)

编排者每轮记录"净进展"。连续 2 轮无净进展就触发卡住处理:
- **进展信号**:测试通过数↑、任务状态推进、新模块集成
- **无进展信号**:测试失败数不变、卡在同一个错误、反复打回同一个问题
- 触发后:走升级阶梯,不是继续原地循环。

## 活锁检测 (Deadlock Detection)

A 等依赖(任务X),X 又在等 A 或绕回 A:
- 编排者周期性检查任务依赖图有无环
- 发现环 → 打破:把循环依赖中的一个任务降级为"独立完成"(先去掉那个依赖)或叫人。

## 预算守护 (Budget Guard)

- **步数预算**:每个任务有步数上限,超限强制停下,产出"卡在哪、已尝试什么、建议怎么办"
- **总预算**:项目级设总token/总迭代数,接近上限时编排者预警,提醒"剩余预算X,是否值得继续或该交付现状"
- 目的:防止"为了一个边角问题烧光所有预算"。

## 子代理粒度与超时降级 (实测补强)

> 实测发现:子代理处理"产出完整代码+验证"这类重任务易超时(曾10分钟超时)。这是真实的执行层风险,必须有护栏。
>
> ⚠️ **2026-07 修订(基于真实使用反馈)**:原 5-10min 墙钟超时过于激进——子代理很多时候在**等 API 响应**(DeepSeek ~60s/次、Tauri build 数分钟)、**跑测试**、**处理难度差异大的任务**,墙钟长 ≠ 死循环。按墙钟一刀切超时 → 几乎所有子代理都被杀 → 降级主会话 → 主模型包揽一切,多智能体团队被架空。
> **修正方向**:超时数值按画像放宽 + **进展检测优先于墙钟**(有进展就不算超时,哪怕墙钟已过基准)。

### 子代理任务粒度上限
派给子代理的任务要**小而专**,避免一个子代理干"大而全"的重活:
- ❌ 错误派法:"实现整个模块+写测试+跑验证+贴输出"——太重,易超时
- ✅ 正确派法:拆成多个小子代理——一个只产出代码、一个只写测试、验证由编排者或独立测试子代理跑
- 经验阈值:单个子代理任务**产出不超过~200行代码或单一职责**,超了就拆

### 超时降级机制（2026-07 修订：进展优先于墙钟）

> ⚠️ **本节"降级为主会话"是 P2(独立生成)画像的默认 handler。其它画像不同**——P1 查证超时→放弃+问人(为 trivial 破隔离不值);**P4 副作用型超时→绝不降级、绝不重试**(不知执行到哪,降级=主会话盲续=可能双写)→停+checkpoint+叫人。完整分流见 `exception-handling.md` 画像总表 + handler 1/5。

**核心原则：墙钟超时不直接杀子代理，先看有无进展。**

子代理墙钟达到画像基准时（P2 基线 15-30min），编排者**不立即中止**，先做进展判定：

1. **有进展**（已产出部分代码 / 测试部分通过 / 有新工具调用输出）→ **续派**：给子代理更多时间，不降级。墙钟基准只是"该看一眼了"，不是"该杀了"
2. **无进展**（连续 2 轮无净进展，见"无进展检测"）→ 走升级阶梯（不是直接降级）
3. **只有"明确死循环 + 无进展 + 已走完升级阶梯"** → 才降级为主会话代行

**为什么这样改**：原设计"墙钟到就杀→降级主会话"，把"等 API 响应""跑测试""处理复杂任务"的合理耗时都当成了死循环，导致几乎所有子代理都被杀、主模型包揽一切、多智能体团队被架空。修正后：**墙钟长但有进展 = 在工作，不打断；墙钟长且无进展 = 真卡住了，走升级**。

降级为主会话代行时（仅 P2/P3 适用，且仅在"无进展+升级阶梯走完"后）：
1. 编排者按画像设子代理超时预算（见 `exception-handling.md` 总表，P2 基线 15-30 分钟）
2. 走完"进展判定→升级阶梯"仍无进展 → 中止子代理，**降级为主会话代行**
3. **必须标注隔离折扣**：主会话代行 = 该任务的"产出方"和"判断方"不再隔离。在事实来源文档活跃上下文（区块2）记"降级:XX任务由主会话代行,隔离折扣"
4. 降级后仍要走交叉核对：主会话产出的代码，验证仍由**另一角色/独立子代理**复现

> 关键：超时降级保住"进度"，但**隔离和交叉核对不能一起降级掉**。产出可代行，验证必须独立。
>
> ⚠️ **墙钟基准是"提醒看进展"，不是"必须杀"**。编排者看到墙钟过基准时第一动作是**查进展**，不是 kill。

## 集成任务路由规则(实测补强)

> 本节是 `exception-handling.md` 画像模型中 **P2(独立生成) vs P3(集成型)的路由实例**。"需看≥2模块实际接口"即 P3 的判定;"步数翻倍"即 P3 相对 P2 基线的预算差异。本节为便捷引用,数值真相以画像总表为准。

> 实测发现:子代理适合"单一职责、独立、小粒度"模块,但**大集成核心(多依赖+复杂状态机)子代理会超时**,且隔离子代理看不到其他模块实际代码,集成易出 bug。所以集成任务有专门路由。

### 派任务前先判"集成型 vs 独立型"
编排者派任务前,判断任务类型:
- **独立型**(单一职责、输入输出清晰、不需看其他模块实际代码)→ 派子代理(隔离产出)
- **集成型**(需看≥2个模块实际代码才能正确写,如状态机整合/适配层/统一导出)→ **编排者直接做**(它的本职,不是降级,见编排者角色"集成授权")

判定标准就一条:**写这代码要不要看其他模块的实际接口?要→集成型→编排者做。**

### 集成任务的预算放宽(对应"超时放宽限制")
集成型任务比独立模块复杂,给编排者做时**放宽步数预算**:
- 独立子代理任务步数上限:默认 50 步(见"预算守护")
- **集成型任务步数上限:翻倍(100 步)**,因为串接多模块+状态机本就更重
- 仍超?→ 拆集成(core 太大就拆成 core-roll/core-rent/core-bankrupt),或叫人
- 放宽的是"预算",不是"验证"——集成产出仍交独立子代理验证

### 并行产出后的接口契约核对
并行产出多个独立模块后,**集成前编排者必须核对接口契约**:
- 各模块的函数签名/状态结构/返回格式是否一致(如 board 的格结构 vs upgrade 假设的格结构)
- 不一致 → 先让相关模块子代理修对齐,再集成
- 这是"并行加速"的必要配套:并行快,但集成前必须有人(编排者)核对一致性,否则集成爆炸

## 检查点与回退 (Checkpoints)

每个内层循环成功退出 = 一个检查点(代码已集成、测试已绿)。卡住时可:
- 回退到上一个检查点(代码回到上一致状态)
- 重新规划当前任务,而非在脏状态上继续打转
- 这保证"卡住不会污染已有成果"。

## 守卫断言 (Invariants)

每个循环有不变式,违反就停(而不是继续跑可能错的):
- 内层循环不变式:"每轮结束时,已有测试全绿或明确知道为何没绿"
- 外层循环不变式:"每条已处理需求都有通过/失败/叫人三种明确终态之一,无悬空"
- 违反 → 编排者停下调查,不继续。

## 编排者的护栏职责

编排者是**唯一持护栏的**:
- 计数每轮循环、判断进展、执行升级阶梯、检测活锁、守护预算
- 其他角色专注做事,编排者专注"这事是否还在轨道上"
- 编排者发现自己也无法判断时 → 叫人(它也有上限)。

## 副作用操作门禁 + 并发上限(指向 exception-handling.md)

这两类是 `guardrails.md` 原缺、由 `exception-handling.md` 补的,编排者同样持此:

- **副作用操作门禁(handler 1)**:任务画像落 P4(副作用型)→ pre-flight 必建幂等令牌+checkpoint;in-flight 任何异常→停+checkpoint+叫人,**绝不自动重试**;post 由测试工程师验副作用态。这是本框架最危险的画像,handler 详见 `exception-handling.md`。
- **并发度上限(handler 6)**:在飞子代理数 ≤ N(默认 4);超限排队不派。
- **熔断(handler 7)**:某子代理/角色连续失败 ≥3 → 停止派发,走升级阶梯。

> 这三条的完整触发/检测/恢复/叫人四要素见 `exception-handling.md`,本节仅声明编排者职责归属。

## 交付/运维边界(非门禁覆盖,实测补强)

> 实测发现(案例A（某回合制 web 游戏） Phase2 HL-004):代码门禁(V-REG/playwright/guard-check --execute)全绿后,把 URL 交付给用户,用户却撞到"must be landed"——因为旧服务器进程没杀净(EADDRINUSE)+ 用户浏览器停在旧游戏,买地请求发到新服务器(新游戏 pos0/phase=rolling)。**所有自动化门禁全绿也挡不住这类运维/客户端-服务器失步**。

这一层**不在代码门禁覆盖范围**(门禁管代码逻辑,不管运行时多实例/客户端同步),单列于此提醒:

- **重启服务器确保杀旧进程**:新服务器起不来的 EADDRINUSE 是表象,根因是旧进程残留;重启前 `netstat -ano | grep :PORT` + `taskkill` 杀净
- **交付 URL 前确认客户端-服务器同步**:服务器 200 ≠ 用户浏览器在最新游戏;交付前让用户刷新一次,或自检"服务器 state == 用户看到的状态"
- **端口/多实例管理**:本地多服务器实例(boot test 残留 / playwright webServer / 主服务)易冲突,要有显式 kill 流程

> 这层的失效只能靠**人验收(门禁5)**显——用户玩到才撞到。所以门禁5不可省,且交付 URL 时要把"客户端是否同步"纳入人验收前的检查。

## 一句话原则

> **系统永远要有出路,且最高出路是"停下来叫人",不是"无限跑下去"。** 撞墙不是失败,撞墙不升级才是失败。
