# 交叉核对与幻觉纠正 (Cross-Verification)

> 防幻觉不能靠"审查者读 diff"单视角。本文定义**发现幻觉 → 纠正 → 防复发**的完整机制。
> 核心原则:**任何"完成/通过/正确"的声明,必须由非作者角色独立复现证据,否则视为未验证。**
>
> ⚠️ **oracle 诚实性补注**:"非作者复现"本身仍是模型声称,除非复现路由进工具执行(`guard-check --execute` 跑区块8.3可执行验证规则)。路由进执行的=**非伪造oracle**(回归/覆盖率/类型/lint/工件落盘/可复现缺陷);未路由的(UI/视觉/设计判断/隔离)=**判断类,无oracle**,靠多视角(红队/交叉核对)+人gate5,不可当oracle级可信。下表"重跑"凡可执行的,均须路由进 `guard-check --execute` 才算非伪造。

## 为什么需要这个

AI 幻觉的特征是**自信地说错的**。单视角审查(审查者一个人读)有两个死穴:
1. 审查者自己也会幻觉,和作者共享盲区
2. "读 diff 觉得对"≠"真的对",只有**复现**才能证伪

所以可靠交付的关键不是"多审几遍",而是**每个声明都由不同视角的人复现一次**。复现失败 = 幻觉被抓住。

## 机制1:全量交叉核对(强制)

**每个"完成/通过/正确"声明,必须由非作者角色独立复现证据。** 不信声明,只信复现结果。

### 核对矩阵(谁核对谁)

| 作者的声明 | 核对者 | 怎么核对 | 通过条件 |
|-----------|--------|---------|---------|
| 开发者:"测试通过" | 测试工程师 | **重新跑一遍测试**,看输出 | 输出确实全绿,且是本轮新鲜结果 |
| 开发者:"修复了bug" | 测试工程师 | **复现原bug的触发条件**,看是否还出现 | bug 不再复现 |
| 开发者:"没破坏其他" | 测试工程师 | **跑回归基线全量** | 基线全绿 |
| 架构师:"放在模块X合适" | 审查者 | **对照ADR区块5**,核模块边界 | 符合既有决策 |
| 测试工程师:"覆盖率达标" | 审查者 | **重跑覆盖率工具**,核数字 | 数字与声明一致 |
| 任何角色:"我完成了" | 编排者 | **要可复现证据**,无证据=未完成 | 证据存在且新鲜 |

### 铁律
- **作者不能自己核对自己的声明**(禁止"我测了,通过"自我闭环)
- **核对必须重新执行**(不是看作者的截图,是自己跑)
- **核对结果回写文档**(区块4/8),带核对者和时间

### 与内层循环的关系
原流程:开发→测试→审查。加交叉核对后:
```
开发者产出 + 声明"完成"
    ↓
测试工程师【独立复现】(不是信声明,是重跑)
    ↓ 复现成功 → 审查者
    ↓ 复现失败 → 标记幻觉,回开发者(走纠正流程)
审查者【独立核对】diff+证据
    ↓ 核对通过 → 集成
    ↓ 核对失败 → 标记幻觉,回开发者(走纠正流程)
```
每次"复现失败"= 抓住一次幻觉,进机制2。

## 机制2:幻觉日志(发现后必记录,防复发)

bug 和幻觉不同:bug 是"代码错了",幻觉是"**自信地声称了不真实的事**"(如声称测试通过但没跑、声称调用了某API但没调、声称符合ADR但没核对)。幻觉必须单独记录,找规律。

### 幻觉日志(事实来源文档新增区块11)

| 字段 | 内容 |
|------|------|
| 幻觉ID | H-001 |
| 声明 | "测试全通过"(开发者说的) |
| 真相 | 测试工程师重跑:3个测试失败,开发者根本没跑 |
| 怎么发现的 | 交叉核对——测试工程师复现时失败 |
| 纠正 | 回开发者,要求真跑+附输出;本次打回 |
| 规律标签 | "完成声明未带新鲜证据" → 加入守卫断言必查项 |
| 关联角色/任务 | 开发者 / T-012 |

### 维护
- 知识管理者维护(每次幻觉发生时记录)
- **定期回看**(每N个迭代):哪类任务、哪个角色、哪类声明最易幻觉 → 针对性加强
- 规律标签**回流到守卫断言**(机制4),把"这次发现的幻觉类型"变成"下次必查项"

> 价值:不纠正单次幻觉,而是**降低未来幻觉率**。同样的幻觉不重复犯。

## 机制3:质疑前移(默认不信任,从开发阶段就攻)

现在红队只在退出门禁前介入。但幻觉在开发阶段就产生。把"质疑"前移:

### 审查者/红队的默认指令(写进角色)
拿到任何声明时,默认假设:
> "这个声明可能是幻觉。证据在哪?能复现吗?是不是编的?"

对每个"完成/通过/符合/没影响"声明,追问三连:
1. **证据**:你声称X,证据(文件/输出/测试结果)在哪?
2. **复现**:这个证据我重新跑一遍,能得到同样结果吗?
3. **来源**:你说的"符合ADR/调用API/没破坏"——你是核对过的,还是推测的?

答不上来 = 推测 = 可能幻觉 → 标记,要求补证据或重做。

### 不只验收时攻
红队的"攻破"不只用在退出门禁。开发阶段的复杂逻辑,红队可被编排者提前调用,对关键模块做"假设这里有幻觉,找出来"的针对性质疑。

## 机制4:可执行守卫断言(每轮必填的闸门)

把 guardrails.md 的文字断言变成**编排者每轮必须填的 checklist**。任何一条不满足 → 不进下一步。

### 每轮结束必填(编排者)

- [ ] 本轮所有"完成"声明,都有**非作者角色复现证据**?(机制1)
- [ ] 所有测试结果是**本轮新鲜重跑**的,不是引用旧的?
- [ ] 有无声明**未带证据**就声称完成?(有→打回)
- [ ] 本轮有无幻觉被抓住?有则记入幻觉日志(机制2)
- [ ] 上轮幻觉日志的**规律标签**,本轮有针对性防范了吗?
- [ ] **本轮是变更场景吗(改了已交付代码)?是→按区块12变更影响记录的验证范围,跑了区块8.3回归套件吗?结果回写8.3"上次运行"且全绿吗?**(回归闸,详见 change-impact-analysis.md)

### 内层循环不变式(违反就停)
- "每轮结束时,每个'完成'声明要么有非作者复现证据,要么被标记为未完成"——没有"声称完成但无人核对"的悬空状态
- "幻觉日志的规律标签,必须反映在守卫断言必查项里"——发现过的幻觉类型,必须成为永久必查项

### 可执行守卫断言(实测补强:从文字checklist变成脚本)

> 实测发现:文字checklist靠人填,容易跳过或敷衍。改成可执行脚本,编排者每轮**必须跑**,脚本输出决定能否进下一步。

脚本 `scripts/guard-check.py`(随本 skill 提供)做两件事:
1. **读事实来源文档**,本轮的"完成"声明逐条核:有没有对应的非作者复现证据(区块4/8/11里有没有独立验证记录)
2. **读幻觉日志(区块11)的规律标签**,把它们输出为"本轮必查项"——发现过的幻觉类型自动成为永久必查

用法:
```bash
python ~/.agents/skills/multi-agent-dev-team/references/scripts/guard-check.py <PROJECT_CONTEXT.md>
```
输出:`GUARD PASS`(可进下一步)或 `GUARD FAIL: <哪条不过>`(必须处理)。

**铁律**:GUARD FAIL 时编排者**不准**宣布该轮完成,必须补齐证据或记幻觉。这把"守卫断言"从"编排者自觉填"变成"脚本卡住不让过"。

### 幻觉规律标签回流(实测补强:落实闭环)

> 实测发现:H-001 的规律标签"完成声明未带文件存在证据"该回流成必查项,但实测中没真做,闭环没跑通。现在落实:

回流机制(由 guard-check.py 自动执行):
1. 扫幻觉日志(区块11)所有规律标签
2. 每个标签 → 生成一条"本轮必查项"(如标签"完成声明未带文件存在证据" → 必查"本轮完成声明是否都有文件存在证据")
3. 编排者每轮跑 guard-check 时,这些必查项**自动出现**,不用人记
4. 即:幻觉一旦被记入日志,它的类型**永久**进入每轮必查,直到人在日志里标注"已系统性消除"

> 这才是真闭环:幻觉发现 → 记标签 → 自动回流必查 → 下次同类必被抓。不是靠人记得防,是脚本强制防。

## 远端 CI:真·不可绕过层(实测补强)

> 实测发现:本地 `guard-check` + pre-commit hook 是第一道闸,但**可被 `--no-verify` 绕过**——本地门禁天生可绕,"不可绕过"因子只有 ~0.7。要真不可绕过,验证须跑在**远端**(开发者碰不到的地方)。

**层级(叠加,非替换)**:
1. 本地 pre-commit hook + `guard-check`——快速反馈,第一道(可绕)
2. **远端 CI**(GitHub Actions 等)——每次 push/PR 自动跑同一套 oracle(测试/coverage/变异/e2e),门在远端,`--no-verify` 失效
3. 分支保护(必需 PR + 状态检查通过 + enforce_admins)——阻断门,坏代码**进不了主干**(CI 红不让合)

**关键认知**:
- 只有②没③ → CI 事后跑(push 后跑,红牌但不阻断落地)→ "不可绕过"~0.85(绕不过,但不挡)
- ②+③ → 真·阻断门 → ~0.95
- 实例:案例A（某回合制 web 游戏） 配了②(远端 CI 全绿),但免费 private 仓库用不了③(GitHub 政策:分支保护需 public 或 Pro)→ 用户选轻档,如实记 0.85 非 0.95,**不假装**。
- CI workflow 须绕开本地脚本可移植性问题:本地 `guard-check.py` 常含绝对路径/特定解释器(`python "C:\...\guard-check.py"`),远端 Linux 路径不存在 + 可能只有 `python3`。**CI 直接跑 oracle 命令**(`npm test`/`npx playwright test`/`node scripts/phase-gate.js`/变异脚本),不套本地 guard-check.py;或把 guard-check 复制进项目用相对路径。

## 机制间的关系(闭环)

```
声明产生
  ↓
机制1 交叉核对(非作者复现)──失败──► 抓住幻觉
  │                                  ↓
  │ 通过                        机制2 幻觉日志(记录+规律标签)
  ↓                                  ↓
集成                          规律标签回流
                                  ↓
                          机制4 守卫断言(把规律变必查项)
                                  ↓
                          机制3 质疑前移(下次默认查这类)
                                  ↓
                              降低未来幻觉率
```

这是"发现→纠正→防复发"的闭环。不是每次重新靠人盯,而是**幻觉一旦被发现,它的类型就永久进入必查清单**,系统越来越难犯同类幻觉。

## 成本说明(你选了全量,这是代价)

全量交叉核对 = 每个声明都要非作者复现。代价:
- 协调成本上升(每个完成声明多一次复现环节)
- 速度下降(尤其并行任务,核对串行化部分)
- 适合:高可靠/高安全/交付级项目。简单原型不推荐(用关键声明核对即可)。

编排者有权按任务风险**降级**:标注为"低风险/原型"的任务,可降为关键声明核对(机制1的部分应用),但必须在文档标注降级理由。

> ⚠️ **"按任务风险降级"现收编为任务画像的"爆炸半径"维函数**(见 `exception-handling.md`)。低风险/原型 = 低爆炸半径画像 → 可降为关键声明核对;高爆炸半径(鉴权·资金·不可逆)→ 不得降级,强制全量交叉核对。本条不再作为独立规则,以画像模型为唯一真相。

## 机制5:子代理输出结构化契约(实测补强)

> 实测发现:审查子代理输出126KB自由散文(逐行代码追踪全写进输出),超传输阈值存成artifact,且artifact格式非标准JSON,编排者无法解析结论。根因:**子代理输出没有结构化契约**——和需求不结构化是同类问题(源头不结构化,下游混乱)。

### 根因(第一性)
子代理的输出是"验证结论的源头"。它不结构化 → 输出过大(无长度约束)+ 格式不可靠(无格式约束)+ 编排者难解析(不知去哪找结论)。和"需求不结构化导致下游全乱"是同一个根因。

### 契约:过程与结论分离 + 结论结构化

**所有产出结论的子代理(测试/审查/红队/调试专家),输出必须分两段:**

#### 段1:结论(结构化、短、必传)
结论必须是固定schema,编排者能直接解析,不靠从散文grep:

**测试工程师结论schema:**
```
{结论: PASS/FAIL, 通过数: N, 失败数: M, 失败项: [{验收标准: "R-xx", 期望: "...", 实际: "..."}], 证据: "跑了什么命令/输出"}
```

**审查者结论schema:**
```
{结论: 放行/打回, 缺陷数: N, 缺陷: [{位置: "文件:行", 问题: "...", 严重度: 高/中/低}], 无新缺陷: true/false}
```

**红队结论schema:**
```
{结论: 通过/攻破, 发现: [{威胁: "...", 复现: "...", 严重度: 高/中/低}]}
```

#### 段2:过程(可长、可截断、不进主输出)
- 详细追踪/分析过程(如逐行代码审查)可写,但**不进主输出**——写到artifact文件或截断
- 过程是给"需要深入看的人"看的,不是给编排者路由用的
- 编排者只读段1(结论)做路由决策

### 为什么必须结构化(和需求结构化同源)
- **防过大**:结论有schema约束,不会无限写散文撑爆输出
- **防格式不可靠**:固定schema = 编排者能解析,不用赌它是JSON还是纯文本
- **防编排者误判**:编排者从结构化结论直接拿到"放行/打回+缺陷列表",不用从126KB散文里找结论(可能找错/漏看)

### 与已有机制的关系
- 这和**铁律4(需求结构化)**是同源道理:源头不结构化,下游混乱。需求结构化管"输入端",子代理输出结构化管"输出端"——两端都结构化,中间才不混乱
- 编排者收到结构化结论后,据此做路由(放行→集成/打回→回开发者),路由决策有据可依
- 幻觉日志(区块11)的记录也受益:结构化结论里的"失败项/缺陷"可直接转成幻觉日志条目

### 实施提示
- 派子代理时,prompt里**明确要求"结论按schema输出,过程分离"**
- 子代理若仍输出散文,编排者可要求重发结论段(不重跑整个分析)
- artifact文件若存过程,文件名带子代理ID+任务ID,便于追溯
