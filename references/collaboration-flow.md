# 协作流程与调度

> **本文件定义"怎么转",另两份定义"怎么不翻车"**:
> - `anti-hallucination.md`——防幻觉7约束(所有角色遵守,尤其"不确定就说不确定""可证伪声明")
> - `guardrails.md`——失控护栏(内层循环上限按画像/P2基线5轮、失败升级阶梯、无进展检测、预算守护)。编排者持此,防止死循环。
> - `exception-handling.md`——异常处理+任务画像驱动限制(同一触发按画像走不同 handler,含副作用门禁/熔断/并发上限)。

## 双层循环(产品交付闭环)

交付稳定产品需要**两层循环**:内层是单次改动的快速反馈,外层是整个需求集的完成判定。两者都不是纯单向流水线。

```
外层 loop(产品级):遍历所有需求直到全部满足
┌──────────────────────────────────────────────────────┐
│ [需求分析师] 取一条需求 → 结构化规约+验收标准 → 交编排者  │
│ [编排者] 分解任务 + 咨询架构师(脱敏)→ 识别依赖与并行组     │
│   ┌── 内层 loop(单次改动级,星型路由,角色互不可见)──────┐ │
│   │                                                      │ │
│   │      编排者(唯一路由器,脱敏转译)                       │ │
│   │       ╱      |       ╲                                │ │
│   │   开发者  测试工程师  审查者  ← 各自独立,互不知对方存在    │ │
│   │   产出diff  独立复现   独立核对                          │ │
│   │      ╲      |       ╱                                │ │
│   │       编排者汇总+判断                                  │ │
│   │         ↓ 复现成功+核对通过                            │ │
│   │       集成 + 知识管理者沉淀(脱敏产出)                  │ │
│   └──────────────────────────────────────────────────────┘ │
│ 还有下条需求? ─否→ 继续                                     │
└──────────────是──────────────────────────────────────────────┘
                    ↓
          产品级退出门禁(见下,5条)
                    ↓
          人的最终验收(不可省)
                    ↓
                交付
```

**隔离协议**:角色之间无直接连线,所有路由经编排者。编排者给每个角色的输入**脱敏**(剥离来源角色身份/声明),让角色互不知对方存在。这让交叉核对的"非作者复现"是真独立——测试工程师不知道有"声明"存在,不会被带偏。详见 `isolation-protocol.md`。

**唯一人参与点有二:需求输入(角色1)+ 最终验收(退出)。** 其余全自动,但每一步都有客观验证信号把关。

### 内层循环:单次改动达标(含交叉核对 + 隔离 + 回归)

> 防幻觉核心:**不信声明,只信非作者复现**。隔离让复现真独立。变更还要跑回归防改坏旧的。详见 `cross-verification.md` + `isolation-protocol.md` + `change-impact-analysis.md`。

- **触发**:开发者产出代码 diff + 声明"完成" → 交编排者
- **流程**(编排者星型路由):
  1. 编排者把 **diff + 验收标准**(剥离开发者声明/身份)给测试工程师 → 测试工程师**独立复现**(它根本不知道有人声称过通过):失败→编排者记幻觉日志→走纠正分支;通过→下一步
  2. 编排者把 **diff + ADR约束 + 05 可审制品(区块8.4,脱敏) + ★上轮 defect list(如非首次) + ★业务验收标准(区块3)** 给审查者 → **审查者必须用 `council-orchestrate`**(★强制多模型:双模型独立审→仲裁→guard-check→delta 回喂,不允许单模型 review 应付)。审查者**独立核对**(审 05 证据是否可信充分,不信通过声明只审证据;静态疑点输出"待验证发现"→编排者转 05→05 回填→06 复核,形成 06 提疑→05 实测→06 复核闭环,受内层循环上限约束):打回→编排者记幻觉日志→走纠正分支;通过→下一步
  3. **回归闸(变更场景)**:若本次改动涉及已交付代码(非新功能),测试工程师按变更影响分析(区块12)定的范围跑**全量回归(经 `guard-check --execute` 独立验证,非伪造)**——非全绿不准集成(防改坏旧的)
  4. 编排者把**脱敏后的已集成产出**给知识管理者沉淀
- **退出条件**:① 测试全绿且为**本轮新鲜复现**;② **★多模型审查通过**(council-orchestrate 全绿,含 delta_review can_release=True);③ 所有"完成"声明都有**非作者复现证据**;④ **变更场景下回归全绿**(无回归失败或已修复)
- **退出动作**:集成 + 知识管理者更新区块7/9/10/11(含幻觉日志)

### 幻觉纠正分支(复现/核对失败时触发)

当交叉核对发现"声明≠真相"(如开发者说测试通过但重跑失败),不简单"重做",走纠正:
1. **标记幻觉**:记入幻觉日志(区块11)——声明/真相/怎么发现/纠正/规律标签
2. **编排者路由回开发者重做**,要求带真实证据(开发者不知道是谁抓的,只收到"这处失败,修")
3. **规律标签回流守卫断言**:该类幻觉成为后续必查项(防同类复发)

这是从"纠正单次"到"降低未来幻觉率"的关键——每次幻觉都让系统更难再犯同类。

### 外层循环:产品级完成判定

遍历所有需求,每条都跑完内层循环。全部处理完后,**不自动宣布交付**——进入退出门禁检查。

### 产品级退出门禁(5条,定义"什么时候算交付稳定产品")

> 前4条客观可判定,第5条必须人。**门禁不是"验证代理觉得满足",而是客观信号全绿 + 人验收。**

| # | 门禁 | 判定者 | 客观? |
|---|------|-------|------|
| 1 | 所有需求的所有验收标准 → 对应测试全部通过 | 测试工程师 | ✅客观 |
| 2 | 质量门禁全绿:区块8.3可执行验证规则全绿(回归/覆盖率/类型/lint) | 测试工程师 | ✅客观(须guard-check --execute) |
| 3 | **★多模型审查通过**(council-orchestrate 全绿:双模型审+仲裁+delta_review can_release=True)+ 无未解决的高优先级审查问题 | 审查者 | ✅客观 |
| 4 | 无未解决的高优先级技术债 | 架构师 | ✅客观 |
| 5 | **人的最终验收**:客户/产品代表确认"满足需求、可交付" | 人 | ⚠️主观,不可省 |

> ⚠️ **收敛与放行硬线(防"带已知缺陷放行")**:门禁3/4允许"只剩低优问题"时放行——收敛判断:审查缺陷数递减时编排者**带低优债放行**,不无限打回(审查总能找到新缺陷)。但有一条硬线:**任何触及 P0 验收标准(区块3.1)的缺陷 = 高优先级,不得降级为低优技术债塞进区块6,不得过门禁3/4**。判定锚定客观:看该缺陷是否导致某条 P0 验收 checkbox 失败——失败即 HIGH,与谁怎么说无关。真打磨项(UI微调/命名/非P0体验)仍可延后。(大富翁实测教训:入狱后状态未清被当低优债放行,实为P0逻辑bug——此硬线即为此补。)

**红队(若启用)在门禁3之后、门禁5之前介入**:模拟真实威胁攻破系统,发现高严重度问题则交编排者路由给修复方(不直连),修完再回红队验证(形成针对红队发现的内层循环),清空后才进入人验收。红队挡的这层缓冲,正是减少人验收负担的关键。

**编排者职责**:收集前4条信号。全绿时**不自动宣布交付**,而是向人(客户/产品)发起最终验收请求,由人拍板第5条。

> ⚠️ **为什么第5条不能省、不能交给AI**:AI 的"没发现错误"不等于"没有错误",更不等于"产品稳定可用"。真实用户场景可能超出测试覆盖;"稳定"和"满足需求"有主观维度。**自动化能保证"通过了我们能做的客观检查",但"交付"最终是人的判断。** 把交付权完全交给 AI 是危险的。
>
> "无逻辑错误"是**不可能绝对保证**的(停机问题/测试不能证明无bug)。门禁能保证的只是"**已知验证手段下未发现错误**"。这就是为什么需要回归基线、审查者、以及人验收的多重把关,而不是单靠某一步。

### 落地后深审(消费区块14,交付后复盘)

> 交付不是终点。过门禁5(人验收)交付后,**专门开一轮深审**,消费区块14(未知/盲区日志)——把"这次不知道的"变"下次知道的"。详见 `anti-hallucination.md` 补注3。

- **触发**:交付后(过门禁5,人验收通过),不卡交付(交付已完成)
- **谁**:编排者驱动,按未知类型 dispatch 04/03/05 补
- **消费区块14 逐条**:
  - 能补实测 → 派 04/05 补(把"推理当验证"的还成实测)
  - 未验证假设 → 人/实验确认
  - 架构盲区 → 03 重新评估该决策
  - 不需深究 → 标记关闭
- **价值**:系统性降盲区。类比区块6(技术债):6=结构债 03 驱动还;14=知识债 落地后深审还。**尤其 04/03**:开发者把"没查当没事"还成"查了确定",架构师把"假设当事实"还成"验证过的决策"。

## 调度步骤(编排者执行)

编排者驱动外层循环。对**每条需求**重复:

1. **接收规约**——从需求分析师拿到结构化需求规约。**前置**:确认该需求涉及的 PRD 章节已 freeze;若 P0 标 `界面交互:是`,还须确认对应 `docs/INTERACTION_SPEC.md` 章节(交互规约章节字段)已 freeze。未 freeze 不准派 dev(防 dev 期间规约漂移)
2. **咨询架构师**——对每个需求问"放在哪个模块?有什么约束?"
3. **分解任务**——拆成可并行、可独立验证的子任务;优先问"这个任务能独立完成并独立验证吗?"
4. **登记任务表**——写入文档区块4(任务ID/负责人/依赖/DoD/产出物)
5. **启动内层循环**(编排者星型路由,角色互不知对方存在):
   - 调度开发者——无依赖任务并行派发(脱敏:只给任务+约束,不给其他角色身份);开发者在动手前必须读文档区块4(自己的任务)、5(约束)、7(模块)、9(踩坑)
   - 触发验证——开发者产出后,编排者把 diff+验收标准(剥离声明)给测试工程师跑客观验证(区块8);失败则编排者记幻觉日志、路由回开发者,内层循环继续
   - 触发审查——验证通过后,编排者把 diff+ADR约束(脱敏)给审查者对抗性审查;审查结论回写区块4;打回则编排者路由回开发者,内层循环继续
6. **内层退出**——测试全绿 + 审查放行 → 集成,更新活跃上下文(区块2)
7. **沉淀**——通知知识管理者更新区块7/9/10
8. **回到步骤1**——取下条需求,直到需求集全部处理完
9. **门禁0:PRD-区块3 一致性审查(06)**——需求集处理完后、进门禁1-5 前,审查者核对 PRD(spec)的机制/数值/异常路径是否都被区块3 验收标准覆盖;不一致项记区块4.2,高优不准进门禁1-5。**判断类,无 oracle,靠人 gate**(同 ADR-05 性质)。**阶段0 未启用 06 时由人执行(人读 PRD vs 区块3);阶段1 起归 06 角色**
10. **退出门禁检查**——门禁0 通过后,收集前4条门禁信号(见上"产品级退出门禁"表)
11. **请求人验收**——门禁0-4全绿时,向人(客户/产品)发起最终验收请求,由人判定门禁第5条

**关键:门禁全绿≠自动交付。** 步骤11的人验收不可省。

## 契约驱动的并行模式(前后端/多侧并行)

> 默认调度是串行(开发者→测试→审查)。但当前后端(或多个契约边界侧)可独立时,串行=浪费时间。并行前提是**契约先定且冻结**——这正是架构师本职(区块5 ADR + 区块7模块边界)。
> 单文件前端项目(如跳房子/大富翁)不触发——它们没有契约边界两侧,走默认串行。

### 何时启用(条件触发,不是默认)
仅当满足**全部**条件才走并行,否则走默认串行:
- 任务可沿**契约边界**切成≥2个侧(如前端/后端,或两个独立服务)
- 每个侧**只看契约**(接口/类型/schema)就能独立完成并独立验证,不需看对侧实际代码
- 契约本身已由架构师写定并落入区块5/7

### 流程
1. **架构师定契约**:接口签名/数据结构/状态形状/错误约定,写入区块5(ADR)+区块7(模块边界)。契约尽量可机器核对(schema/类型)。
2. **pre-fork 契约审查(强制)**:编排者把契约(脱敏)交审查者核对"契约是否满足区块3的P0需求"——契约错则两侧建在沙上,所以契约本身先过审。打回→架构师改契约,不fork。
3. **契约冻结**:fork 后契约**冻结**。任一侧发现契约不可行→编排者决定:改契约(=重新fork,已建半的产出标废弃或迁移)或叫人。不允许两侧各自悄悄偏离契约。
4. **并行 fork**:编排者同时派≥2个隔离子代理,每个只拿到契约(不给对侧代码/身份)——隔离比串行更强(连"对侧存在"都不知)。各侧跑自己的内层循环(开发→测试→审查,按各自任务画像的循环上限——P2基线5轮——各自计)。
5. **集成前契约核对**:各侧产出后,编排者**先核对接口契约一致性**(各侧签名/结构/返回是否对得上契约)——不一致先让相关侧修对齐,再集成。复用 guardrails.md"并行产出后的接口契约核对"。
6. **集成(编排者做)**:契约边界的胶水/适配层是集成型代码(需看≥2侧实际接口)→ 按ADR-02归编排者,不派子代理。集成产出仍交独立子代理验证(契约边界真的通了吗)。

### UI 侧特例(并行模式里前端=UI 时的追加)
并行模式默认前后端对称,但 UI 侧有三个后端没有的要求,fork 前必须满足:
1. **早期审美 gate**:UI 审美方向(design 角色产 imagegen-frontend-* 设计参考图)是判断类,**人批准后才 fork 实现**——不能 defer 末尾(末尾才发现不喜欢=整个 fork 白做)。后端无此步。
2. **契约含 UI 结构验收**:UI 侧契约不能只有 API,还须含 UI 结构验收(有哪些屏/交互/a11y/响应式)——这是 UI fork 可被 oracle 验的依据。
3. **末尾 UI oracle**:UI 实现的 8.3 规则含 V-UI-STRUCT★/V-VISREG/V-A11Y(Playwright/截图diff/axe,项目 devDep,guard-check --execute 跑)。审美部分仍走早期人 gate,不进 8.3。

> UI 的"并行"= 审美先批 → 实现并行 fork → 可执行部分末尾 oracle;不是"UI 和后端一起 defer 末尾人看"。

### 与已有机制的关系(不矛盾)
- **隔离**:并行模式隔离更彻底(只给契约),不削弱
- **ADR-02集成授权**:集成仍归编排者,并行只加速"各侧实现",不改变"谁集成"
- **guardrails并行核对**:本模式步骤5就是它,复用不重复
- **预算**:两侧各跑内层循环,成本约2x,但外层收敛比串行快——并行换时间,不是免费
- **回归**:集成后跑区块8.3可执行验证规则(契约边界集成是变更场景,走回归闸;UI 侧含 V-UI-* 规则)

### 阶段0:人 + 单智能体,跑通核心管道
- 把 `project-context-template.md` 复制到项目根目录,命名 `PROJECT_CONTEXT.md`
- 填写区块1(项目身份,含 PRD 路径 + 交互规约路径引用)、3(第一条需求)

- 需要部署/CI → 加 **DevOps**

## 单模型下的质量保证

既然多角色常共用同一模型,质量保证全部来自结构(见SKILL.md四层结构)。**测试工程师和审查者是质量的最后两道闸**——给它们最严格的prompt、最窄的上下文、最对立的目标:

- 测试工程师目标:**"证明它不行"**,只信测试信号
- 审查者目标:**"假设有至少3个问题"**,专查边界/并发/错误恢复

## 风险提醒

1. **逻辑复杂 + 全自动 = 最高危**。完全依赖测试和审查。审查者应定期抽审测试质量(测试也可能写错/写假)。
2. **PRD 级设计缺陷在阶段0前置就该暴露**(01 预检 + 数值预估),别等持续迭代——PRD 糊则区块3 结构化也白搭(垃圾进垃圾出)。代码结构级设计缺陷才靠阶段2 架构师 + 持续迭代暴露。
3. **单模型下审查者不能松**。一个松垮的审查者会让整个团队质量塌方。
