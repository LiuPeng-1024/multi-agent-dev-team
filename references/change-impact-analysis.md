# 变更影响分析 (Change Impact Analysis)

> **持续交付的命脉**:真实产品/服务是持续迭代的,改旧功能是常态。任何变更(需求/代码/架构)动之前,必须先评估"会破坏哪些已交付的东西",不评估不准改。
> 这道闸防的是:改了需求2,悄悄坏了依赖需求2的需求4,到用户才发现。

## 为什么这道闸关键(第一性)

前几轮防幻觉都针对"新功能"(从0到1):需求结构化、交叉核对、回归基线。但持续交付的真实场景是**改已交付的东西**——而改旧东西不评估影响 = 定时炸弹。

- 需求变:改了R-02的逻辑,依赖R-02旧行为的R-04会坏
- 代码变:改了 board.js 的格结构,upgrade/mortgage/auction 假设的格结构会失效(大富翁实测就差点踩这个)
- 架构变:改了模块边界,集成层 core 的串接会断

**评估影响 = 在动之前先问"这一改,哪些已交付的要跟着改/重测"**。不问就改,就是拿已交付的部分赌博。

## 什么时候触发(三类变更)

| 变更类型 | 触发时机 | 谁评估 |
|---------|---------|--------|
| **需求变更** | 人改了需求规约(区块3),或废弃/新增需求 | 需求分析师评估(影响哪些已交付需求)+ 架构师评估(影响哪些模块) |
| **代码变更** | 开发者要改已存在的代码(非新写) | 架构师评估(影响哪些模块/集成层)+ 测试工程师评估(哪些回归要跑) |
| **架构变更** | 要改模块边界/ADR | 架构师评估(影响哪些模块+集成层) |

## 变更影响分析的步骤(强制)

**任何变更动之前,必须走完这5步,否则不准改:**

1. **描述变更**:改什么(需求/代码/架构)、改成什么样
2. **识别影响范围**:扫事实来源文档——
   - 需求层:哪些已交付需求(R-xx)依赖被改的旧逻辑?(查区块3的依赖关系)
   - 模块层:哪些模块的接口/假设依赖被改的部分?(查区块7模块索引 + ADR)
   - 集成层:core/适配层是否串接了被改的部分?(查架构师)
3. **标记受影响项**:在事实来源文档新增"变更影响记录"(区块12,见下)列出受影响的 R-xx/模块
4. **定验证范围**:受影响的每个 R-xx → 必须重测其验收标准;受影响的每个模块 → 必须跑**区块8.3回归套件(全量)**+ 集成回归。**结果回写区块8.3"上次运行"**(带时间+全绿状态)——回归证据要新鲜可追溯,不是叙事。无套件则本次变更先建套件再跑(无套件变更=裸奔)
5. **得变更许可**:影响范围明确+验证范围定好,才算"变更许可"——开发者才能动。无许可不准改

## 借力已有 skill

- **`gitnexus-impact-analysis`**:改代码前评估"改这里会崩什么"——这正是变更影响分析在代码层的工具
- **`gitnexus-refactoring`**:重构(一种变更)时安全做法

## 与回归自动化的配合(闸2)

变更影响分析回答"**会坏哪些**",回归自动化回答"**坏没坏**":
- 闸1 识别受影响范围 → 闸2 对受影响范围跑**区块8.3可执行验证规则**(经 `guard-check --execute` 独立验证,非伪造) → 全绿才算变更完成

两闸联动:评估影响→定回归范围→跑回归→全绿→变更完成。少了任一,变更就是裸奔。

## 计划逻辑审查(实施前,实测补强)

> 实测发现(案例A（某回合制 web 游戏） Phase2):计划阶段对计划本身做"改后查逻辑错误",一次抓到 8 处(循环依赖/AI 遇 choice 死锁/漏 toGameState 投影/choose 后 phase 未定义/...),全在写代码前修了,避免它们变成运行时 bug。这是铁律5"改后查逻辑错误"的**前移**——不只改完查,计划写完也要查。

计划定稿后、动手实施前,对计划做逻辑审查,重点查:

- **循环依赖**:任务 A 依赖 B 产出、B 又依赖 A(如 T-101 引用 T-106 的图、T-106 依赖 T-101 的引用)
- **漏投影/接口**:新加的状态字段/契约,前后端是否都接(toGameState 投影、API 端点、契约 schema)
- **未定义状态**:某操作完成后系统处于什么状态(如 choose() 后 phase 落到哪)——未定义会卡死下游
- **死锁路径**:某场景下无人能行动(如 AI 回合遇到需要人选择的机制,AI 不等人→挂死)
- **职责错位**:某任务塞了不属于它的职责(如把故事状态管线塞进 choice 引擎任务)
- **双源真相**:两处定义同一概念(如画像模型与旧"独立/集成"规则平行)——会漂移

> 这条不重编号铁律5(避免触发 SKILL.md 措辞同步),作为铁律5的强化补注:**改前评估影响 + 计划查逻辑 + 改后查逻辑错误**三步。计划查的成本远低于运行时修(8 处在计划阶段 5 分钟审完,若流到代码要 8 次回归红)。

## 与已有机制的关系

- 这道闸在**变更时**触发,不是每次开发。新功能(从0到1)不需要它,改旧功能才需要
- 它补的是"持续交付"维度——前几轮防幻觉都针对"单次交付",这道闸针对"改已交付的"
- 架构师角色的"影响分析"职责原本只在改代码时,现在扩展到改需求/架构也触发
