# 隔离协议 (Isolation Protocol)

> **全隔离原则**:每个角色只知道自己该知道的。角色之间**互不知道对方存在**——不直接通信、看不到对方内部状态/对话/声明。编排者是唯一路由器,所有角色只对接编排者。

## 为什么必须隔离

不隔离的危害:
1. **声明污染**:测试工程师若看到"开发者说测试通过了",会被声明带偏,不是真独立复现(交叉核对失效)
2. **视角同化**:角色互相看到对方推理,会共享盲区,失去"不同视角"的价值
3. **责任模糊**:谁都能看到谁,出错时难定位

隔离后:每个角色**只收到编排者构造的、脱敏过的输入**,独立判断。这才是真独立——交叉核对的"非作者复现"才有意义。

## 技术前提:用子代理实现

本框架基于 ZCode 子代理(subagent)机制。子代理**天然隔离**:
- 独立 context,不继承主会话历史
- 只看到你传给它的 prompt(指令),那是它的全部世界
- 看不到主会话、看不到其他子代理

参考 skill:`dispatching-parallel-agents`、`subagent-driven-development`。
**不要用"单会话内扮演多角色"**——同 context 无法隔离,所有"角色"其实看到全部历史。

## 子代理能力探测 + 主会话落盘折扣(实测补强)

> 实测发现:并非所有子代理类型都有写文件能力(如只读探索型子代理)。开发者子代理可能无法真正落盘,需主会话代落盘——这会削弱隔离纯度。

### 派任务前先探测能力
编排者派"产出代码"类任务前,先确认子代理类型有无 Write/Edit 工具:
- **有写权限** → 子代理独立产出+落盘,隔离纯
- **无写权限(只读)** → 启动"主会话落盘折扣"模式(见下)

### 主会话落盘折扣模式
当子代理只读、无法落盘时:
1. 子代理产出**代码内容**(在它的隔离 context 里生成,判断是独立的)
2. **主会话**负责把代码写到磁盘(代落盘)
3. **必须标注折扣**:在事实来源文档活跃上下文(区块2)记"折扣:XX任务由主会话代落盘,产出方(子代理)与落盘方(主会话)分离"
4. **隔离保留了什么**:产出方的**判断**仍是独立的(子代理在隔离 context 里决定写什么代码,没被其他角色带偏)
5. **隔离损失了什么**:主会话既看了子代理的产出过程又落盘,主会话"知道"了产出细节——若主会话同时扮演验证方,隔离就破了

### 关键:折扣不能传染到验证
主会话代落盘 OK,但**验证必须由独立子代理做**(不能主会话既落盘又验证自己落的盘)。即:
- 产出可代落盘(隔离折扣,可接受)
- 验证不可代行(必须独立子代理,否则交叉核对失效)

> 这条把"隔离折扣"限制在产出环节,保住验证环节的独立性。实测中 H-001(未落盘幻觉)正是靠"验证由独立子代理做"才抓到的——即使产出方有折扣,验证独立就还能抓错。

## 编排者做集成 = 本职,不是折扣(实测补强)

> 实测发现:把"编排者做集成"当成"隔离折扣"是误判。编排者本就是"唯一看全局的角色",集成(串接多模块)天然归它。

### 澄清:集成不是折扣
- **产出独立模块**(board/cards 等)→ 派隔离子代理,隔离纯
- **集成型代码**(core/index/适配层,需看多模块实际代码)→ 编排者直接做,**这是它的本职**,不是隔离被打折
- 判定:写这代码要不要看其他模块实际接口?要→集成型→编排者做(详见 guardrails.md "集成任务路由规则")

### 为什么不算折扣
隔离的目的是"让核对者不被产出方带偏"。集成型代码由编排者写,**验证仍由独立子代理(测试/审查)做**,所以交叉核对没破——编排者写,测试/审查独立验,幻觉照样能抓。破的只是"产出方的隔离",而集成本就不该派给隔离子代理(它看不到全貌,写了也是错)。

### 唯一要守的:集成产出必须独立验证
编排者写完集成代码,**不能自己验**。必须派测试/审查子代理独立核。这条不放宽——否则"看全局的写+看全局的验"闭环,幻觉抓不到。授权放宽的是"写",不是"验"。

## 三条隔离规则

### 规则1:角色文档不提其他角色
角色文档里**禁止出现其他角色的名字**。不写"交测试工程师验证",写"交编排者"。角色只知道自己做什么、对接编排者,不知道团队里还有谁。

### 规则2:编排者构造脱敏输入
编排者给角色的输入,**过滤掉来源信息**(谁产生的、有没有人声称过什么):

| 错误(泄露来源) | 正确(脱敏) |
|---------------|-----------|
| "开发者说测试通过了,你核对一下" | "这是代码 diff 和验收标准,跑验证,报告结果" |
| "审查者发现3个问题,你修一下" | "这3处需要修复:[问题清单],修完交编排者" |
| "架构师说放在模块X" | "这个改动的目标模块是X(依据ADR-07),约束:[约束]" |
| "这是开发者写的代码" | "这是待验证的代码 diff" |

关键:**测试工程师绝不能知道有"声明"存在**。它只收到代码+验收标准,自己跑,独立判断。这样它的复现才是真独立——不被"作者说通过了"带偏。

### 规则3:产出回编排者,编排者转译
角色产出 → 交编排者 → 编排者判断+转译给下一个角色(脱敏):
- 测试工程师报告"3个失败" → 编排者收到 → 给开发者的不是"测试工程师说3个失败",而是"这3个测试失败,修复"
- 开发者**不知道**是谁跑的测试、有没有人核对过

编排者是唯一"知道全貌"的:它知道谁产出了什么、谁该接什么。但它给每个角色的,都是脱敏过的最小必要信息。

## 星型路由架构

```
              编排者(唯一知道全貌+路由)
             ╱      |       ╲
            ╱       |        ╲
       开发者   测试工程师   审查者   (红队)
       ↑↓        ↑↓          ↑↓      ↑↓
     只经编排者 只经编排者  只经编排者  只经编排者
       
  角色之间:无直接连线,互不知道对方存在
  每个角色的上下文:只有"我的任务"+"编排者给的脱敏输入"
```

对比旧的"角色直连"流程(开发者→测试→审查),星型路由多一层编排者转发,但**这是隔离的代价,也是交叉核对能成立的代价**。

---

## 交叉核对在隔离下怎么跑(关键)

隔离不但不妨碍交叉核对,反而让它**更纯**:

1. 开发者产出代码+声明"完成" → 交编排者
2. 编排者把**代码 diff + 验收标准**(剥离开发者声明)给测试工程师
3. 测试工程师**独立跑**——它根本不知道开发者声称过通过,所以不会被带偏,是真独立复现
4. 结果回编排者:
   - 复现成功 → 编排者把 diff+证据(脱敏)给审查者核对
   - 复现失败 → 编排者记幻觉日志,把"失败信息"转给开发者(不说"测试工程师发现的")
5. 审查者同样:只收到 diff+ADR约束,独立核对,不知道有谁声明过什么

**测试工程师不知道"声明"存在 = 它的复现不可能被声明污染 = 真独立。** 这是隔离和交叉核对互相成就的地方。

---

## 编排者的隔离职责(checklist)

每次路由前,编排者自检:
- [ ] 给角色的输入里,有没有泄露"谁产生的/谁声称了什么"?有→脱敏
- [ ] 给角色的输入里,有没有不必要的全局信息?有→删到最小必要
- [ ] 角色产出转给下一个时,有没有带上"来源角色"信息?有→剥离
- [ ] 幻觉日志记录时,关联角色字段是编排者自己填的,不让角色看到日志全貌

## 例外:角色需要知道的"约束"不算泄露

架构约束(ADR)、验收标准、技术约束——这些是**任务输入**,不是"其他角色的存在"。给开发者 ADR 约束不算泄露架构师的存在(开发者只知道"有这个约束",不知道"架构师这个角色")。

边界:**事实/约束可以共享,角色身份/声明/对话不能共享**。

---

## 代价(诚实)

全隔离的代价:
- 编排者负担重(所有路由、脱敏、转译都它干,可能成瓶颈)
- 多一层转发,速度下降
- 角色无法"主动求助"其他角色(只能经编排者)

适合:高可靠、需真独立验证的场景。简单协作可降级为"半隔离"(知道有其他角色但不直连)。
