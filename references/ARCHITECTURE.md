# 整体架构梳理 (Architecture Overview)

> 本文是 multi-agent-dev-team 框架的**顶层综合视图**:一页看懂整个框架如何交付稳定可靠产品。读本文得"全局";读各机制文件(`guardrails.md`/`anti-hallucination.md`/`exception-handling.md` 等)得"深度"。
>
> 本文是各机制文件的**综合**,不是替代——细节以各文件为准。若本文与某机制文件冲突,以机制文件为准。

---

## 0. 一句话定位

把软件项目当作一支**专业化团队**推进——产品/架构/开发/测试/审查/知识管理各司其职,围绕一份**事实来源文档**协作,靠**规格化(产PRD+交互规约)+ 双层循环 + 三层安全系统 + 人验收闭环**交付稳定产品。本 skill 是 superpowers 生态的**上层编排层**(内部仍调用单点 skill),不是替代。

## 1. 分层架构总览

```
┌──────────────────────────────────────────────────────────┐
│ 交付闭环层  退出门禁5条 + 人最终验收(交付权最终在人)        │ ← 何时算"稳定交付"
├──────────────────────────────────────────────────────────┤
│ 安全系统层  ①防幻觉 ②防失控 ③异常处理+任务画像             │ ← "可靠稳定"的核心
│ (可靠三基石)  发现→纠正→防复发 / 撞墙→升级→叫人 / 按场景分流 │
├──────────────────────────────────────────────────────────┤
│ 协作流程层  双层循环(内层单次改动/外层需求集)+ 星型路由      │ ← 怎么转
│             + 契约驱动并行 + 信息隔离                       │
├──────────────────────────────────────────────────────────┤
│ 角色层     10角色(8核心+2可选),目标对立制造行为多样性        │ ← 谁来做
├──────────────────────────────────────────────────────────┤
│ 团队大脑层  PROJECT_CONTEXT.md(区块0-14,单一事实来源)       │ ← 共同记忆
├──────────────────────────────────────────────────────────┤
│ 设计哲学    专业化团队 + 事实来源文档 + 单模型下四层结构保质  │
└──────────────────────────────────────────────────────────┘
          横切: 验证强度阶梯L0-L4 + 保证度三因子(乘法度量)
```

> 注:协作流程层现以**规格化阶段**(产 PRD + 交互规约 → 06 审 → 人 gate → freeze)为前端,先于双层循环;团队大脑层除 PROJECT_CONTEXT 外,还引用 `docs/prd.md`(01 生产)与 `docs/INTERACTION_SPEC.md`(01+03 co-author)两类独立制品(见 §2/§4)。

**可靠稳定主线**:从下往上,每一层都对"稳定"有贡献,但**安全系统层(三基石)是核心**——它把"AI 会幻觉/会失控/会一刀切处理失败"这三个最大风险系统化兜住。

## 2. 团队大脑层:事实来源文档(区块 0–14)

所有角色动手前先读对应区块,产出后更新对应区块。**不更新文档的产出=未交付。** 详见 `project-context-template.md`。

| 区块 | 名 | 作用 |
|---|---|---|
| 0 | 文档元信息 | 版本化(改错可回退)+ 各角色读写速查 + 拆分时机 |
| 1 | 项目身份与意图 ★入口 | 新会话第一站;引用 PRD 路径 + 交互规约路径 |
| 2 | 活跃上下文 ★工作内存 | 编排者维护,context压缩后恢复状态(含降级/折扣标注) |
| 3 | 需求与验收 ★唯一人参与区 | P0全结构化(含界面交互/交互规约章节/PRD章节,异常/边界必填),P1/P2可简化 |
| 4 | 当前任务状态 ★调度依据 | 任务表(含**画像+检查点**两列)+ 审查结论 |
| 5 | ADR | 架构决策记录,改代码前必查 |
| 6 | 技术债台账 | 不还债,代码增长→开发速度趋零 |
| 7 | 模块索引 | 找东西先查这 |
| 8 | 验证与质量状态 ★命脉 | 8.1测试/8.2门禁/8.3可执行验证规则(非伪造oracle,含检查7) |
| 9 | 踩坑日志 | 根因比表象重要10倍 |
| 10 | 变更历史 | 回溯"为什么X变成Y" |
| 11 | 幻觉日志 | 自信地说错的(≠bug),规律标签回流必查项 |
| 12 | 变更影响记录 ★持续交付命脉 | 改已交付的先评估影响+定回归范围+得许可 |
| 13 | 设计系统与审美决策 ★UI 视觉锚点 | design 主笔,memorable-thing/DESIGN.md/taste-profile,0.0e 人 gate |
| 14 | 未知/盲区日志 ★落地后深审 | 诚实自检的不确定项(不 gate,落地后深审消费),尤其 04/03 填 |

**三类制品**(区块1 引用):
- `PROJECT_CONTEXT.md` — SSOT,14 区块,团队大脑(各角色按 0.1 规约读写)
- `docs/prd.md` — 01 生产,产品级(愿景/机制/数值/美术方向),人读 + 01 预检
- `docs/INTERACTION_SPEC.md` — 01+03 co-author(§3 状态/数据契约归 03),实现级,§6 回归断言喂 V-UI-STRUCT

> **PRD ≠ 区块3**:PRD 是产品叙事(人读),区块3 是结构化机器可判定验收(test/review agent 读);不同受众/变更频率→分离。交互规约独立成文(变更频率介于 PRD 与代码之间,不进 SSOT)。

## 3. 角色层:10 角色(目标对立制造多样性)

单模型下角色差异**不来自模型能力**,来自四层结构:①目标函数不同 ②工具授权不同 ③上下文范围不同 ④行为指令不同。详见 `roles/`。

| # | 角色 | 目标函数 | 工具授权 | 内化子技能 |
|---|---|---|---|---|
| 1 | 需求分析师 | 消除歧义 | Read+提问 | **问题空间(假设/成功指标)**、产PRD+交互规约、需求结构化 |
| 2 | 编排者 | 高效调度 | 全调度(不写独立模块,可写集成) | **任务画像判定**、任务分解、依赖管理 |
| 3 | 架构师 | 结构健康 | 只读代码+写决策 | 系统设计、技术债治理、**交互规约§3**、变更影响分析 |
| 4 | 开发者 | 完成需求 | Edit/Write/Bash | 前端+后端+测试编写(UI设计已剥离给 design)+**副作用硬停** |
| 5 | 测试工程师 | 证明它不行 | Bash(不可改实现) | 测试策略、属性/模糊测试(L1)、边界覆盖 |
| 6 | 审查者 | 找出缺陷 | 只读 | 对抗性审查、盲点捕捉、边界/并发/错误恢复、**设计完备性审(第11条)** |
| 7 | 知识管理者 | 记忆完整 | 全文档读写 | 文档维护、上下文持久化 |
| 8 | 设计师 | 提议审美 | Read+WebSearch+提问(不写业务代码) | **memorable-thing**、DESIGN.md、Research三层+Eureka、taste-profile |
| **9** | **红队(可选)** | **攻破系统** | Bash+攻击脚本 | 威胁场景、恶意输入、并发/安全 |
| **10** | **调试专家(可选)** | **找根因** | 只读+Bash诊断 | 根因分析、不盲改 |

> 多样性来自**目标对立**:开发者=完成,测试=让它失败,审查=找缺陷,设计师=提议审美,红队=攻破,调试专家=找根因不盲改。同一模型,目标对立,行为就分化。

## 4. 协作流程层:规格化 + 双层循环 + 星型路由

详见 `collaboration-flow.md` + `isolation-protocol.md`。

### 规格化阶段(产 PRD + 交互规约,dev 不许开工直到 freeze)

> 流程最前端,原缺失——PRD 假设"已存在",交互规约根本不存在,UI 交互只用散文、无 oracle。补上后才闭合。

```
0.0a 01 问题空间(借 brainstorming;禁止写功能):问题陈述+JTBD+发现清单+假设清单(每条 已验证/未验证)+成功指标(outcome)+优先级理由
   ↓
0.0b 早期人 gate ★: 人确认"这是我要解决的问题 + 判断成功的标准"(治"做出来不是我要的";磨尖"需求输入",非新参与点)
   ↓
0.0c 01 起草 docs/prd.md(喂 0.0a)+ 01+03 co-author docs/INTERACTION_SPEC.md(§3 归 03)
   ↓
0.0d 多角色评审(04/05/design 各提疑问)→ 06 综合(第8条 交互规约完备性 + 第9条 问题空间完备性 + 汇总疑问)
   ↓ 打回则回 01 修
0.0e 人 gate(美术/UX 方向 + 待定项决策,ADR-05 前置)
   ↓
0.0f ★ freeze ★  (契约冻结,同并行模式原理;未 freeze 不准派 dev)
   ↓
01 结构化进区块3(P0 标 界面交互:是/否 + 交互规约章节:§y + PRD章节:§x + 假设(带验证状态))
```

- **freeze 才准开工**:交互规约未 freeze,dev 不许动 UI(防 dev 期间规约漂移)
- **检查7**(guard-check):`界面交互:是` 的 P0 须有非空交互规约章节 + 区块1 声明的 INTERACTION_SPEC.md 落盘(弱 oracle,迁移期 warn)
- **门禁0**:PRD-区块3 及 交互规约-区块3 一致性(06 审,freeze 前 + 末尾双重)

### 双层循环(交付闭环)

```
外层 loop(产品级):遍历所有需求直到全部满足
┌────────────────────────────────────────────────────┐
│ [需求分析师] 取需求(freeze后)→结构化规约+验收标准     │
│ [编排者] 分解+咨询架构师→识别依赖与并行组(先定画像)   │
│   ┌── 内层 loop(单次改动,星型路由,角色互不可见)──┐  │
│   │    编排者(唯一路由器,脱敏转译)                 │  │
│   │     ╱      |       ╲                          │  │
│   │  开发者  测试工程师  审查者 ← 各自独立,互不知对方│  │
│   │  产出diff  独立复现   独立核对                   │  │
│   │     ╲      |       ╱                          │  │
│   │    编排者汇总+判断(复现成功+核对通过→集成)      │  │
│   └──────────────────────────────────────────────┘  │
└──────────────────是──────────────────────────────────┘
                    ↓
      产品级退出门禁(门禁0一致性 + 1-4客观 + 5人验收) → 交付
```

- **内层循环退出**:测试全绿(本轮新鲜复现)+审查放行+所有完成声明有非作者复现证据+变更场景回归全绿
- **星型路由**:角色间无直接连线,所有路由经编排者;编排者给每个角色**脱敏输入**(剥离来源/声明),让交叉核对的"非作者复现"真独立

### 契约驱动并行(条件触发)

前后端/多侧可独立时,契约先定且冻结→并行 fork(各侧只拿契约)→集成前核对接口契约→编排者集成(集成产出交独立子代理验证)。UI 侧特例:审美早期人 gate + 末尾可执行 oracle(V-UI-STRUCT,断言来源=INTERACTION_SPEC.md §6)。

## 5. 安全系统层:可靠稳定的核心(三基石)

这是"稳定可靠"的全部来源。**不是可选增强,是框架的安全系统。**

### ① 防幻觉(`anti-hallucination.md`):发现→纠正→防复发

AI 会**自信地产生幻觉**。"验证而非信任"是底线但不够。

- **7 约束**:工具锚定 / 事实推测分离 / 可证伪声明 / 关键决策双重确认 / 引用追溯 / 不确定就说不确定 / 小步快验
- **假绿风险**:测试本身可能假绿(并行共享文件竞态等),凡偶红当假绿嫌疑查基础设施
- **发现纠正闭环**:全量交叉核对(非作者复现)→幻觉日志(规律标签)→标签回流必查项→系统越来越难犯同类

### ② 防失控(`guardrails.md`):撞墙→升级→叫人

多智能体最大工程风险是**失控**:死循环、活锁、预算爆炸。

- 循环上限 / 无进展检测 / 活锁死锁检测 / 检查点回退 / 守卫不变式(违反就停)
- **失败升级阶梯**:重试→换角度→换角色→重新分解→**叫人**(到顶一定是人)
- 预算守护 / 子代理粒度上限 / 超时降级
- 默认值是 **P2 基线**,被任务画像覆盖;升级深度按画像

### ③ 异常处理+任务画像(`exception-handling.md`):按场景分流 handler

> guardrails 管"流程控制"(一律撞墙→叫人);本层管"按场景的失败 handler"(可恢复错误有自愈路径)。**同一触发,不同画像走不同恢复。**

**任务画像**(5维→5具名画像):
- P1事实查证 / P2独立生成 / P3集成型 / **P4副作用型(危险)** / P5探索R&D
- **严者胜**:任一维副作用→套P4;**默认从严**:存疑套更严
- 编排者派任务前用**4问决策树**定画像(副作用维必答)

**画像→(限制+handler)总表**(数值与handler都随画像变):

| 画像 | 超时(墙钟基准) | 循环 | 超时handler | 关键差异 |
|---|---|---|---|---|
| P1查证 | 60s | 1-2轮 | 放弃+问人(不降级) | trivial不破隔离 |
| P2生成 | **15-30min** | 5轮 | **先查进展**:有进展→续派;无进展→升级→走完才降级 | 幂等可自由重试 |
| P3集成 | **30-60min** | 100步 | N/A | 编排者做 |
| **P4副作用** | **按操作耗时调**(快5min/慢可30min+) | 2-3轮 | **绝不自动重试** | 停+checkpoint+叫人 |
| P5探索 | 按预算不按时间 | 宽 | 容忍死胡同 | 按预算不按轮 |

> **进展优先于墙钟**(2026-07 修订):墙钟达基准时编排者**第一动作是查进展,不是 kill**。有进展→续派;无进展→走升级。防止"等API/跑测试的合理耗时"被误判为死循环导致主模型包揽一切。详见 `exception-handling.md` 画像总表。

**补的6+1个原缺handler**:副作用门禁 / 工具失败分流(瞬时vs永久) / 非超时崩溃 / context溢出 / 幂等重试约束 / 并发上限 / 熔断

> **收编声明(防双源真相)**:guardrails 的"独立vs集成"路由=P2/P3实例;cross-verification 的"验证强度按风险降级"=爆炸半径维函数;平铺默认=P2基线。画像模型是唯一真相,旧规则不再独立。

## 6. 交叉核对(`cross-verification.md`):不信声明,只信非作者复现

| 机制 | 作用 |
|---|---|
| 1 全量交叉核对 | 每个完成声明由非作者角色独立复现证据,复现失败=幻觉被抓 |
| 2 幻觉日志 | 记声明/真相/怎么发现/规律标签,标签回流必查项 |
| 3 质疑前移 | 审查者/红队默认不信任,追问"证据/复现/来源"三连,开发阶段就攻 |
| 4 可执行守卫断言 | `guard-check.py` 每轮必跑,**P4任务无checkpoint→FAIL**;**检查7:界面交互:是 须有交互规约章节+INTERACTION_SPEC落盘**(迁移期warn),文字checklist变脚本卡住 |
| 5 子代理输出结构化契约 | 过程与结论分离,结论按固定schema(防126KB散文不可解析) |
| 远端CI | 本地hook可绕→远端CI→分支保护阻断门(真·不可绕过) |

## 7. 交付闭环层:退出门禁 + 人验收

**门禁全绿≠自动交付。** 编排者收集门禁0(一致性,判断类)+ 前4条客观信号,全绿时**向人发起最终验收请求**,由人拍板第5条。详见 `collaboration-flow.md`。

| # | 门禁 | 判定者 | 客观? |
|---|---|---|---|
| 0 | PRD-区块3 及 交互规约-区块3 一致性 | 审查者 | ⚠️判断类,人gate |
| 1 | 所有验收标准→测试全通过 | 测试工程师 | ✅ |
| 2 | 质量门禁全绿(8.3可执行规则,含检查7) | 测试工程师 | ✅(guard-check --execute) |
| 3 | 无未解决高优先级审查问题 | 审查者 | ✅ |
| 4 | 无未解决高优先级技术债 | 架构师 | ✅ |
| 5 | **人的最终验收** | 人 | ⚠️不可省 |

> **收敛硬线**:门禁3/4允许"只剩低优"时放行(不无限打回),但**触及P0验收标准的缺陷=高优先级,不得降级为低优债,不得过门禁**。

## 8. 横切:验证强度阶梯 + 保证度度量

**L0-L4 阶梯**(怎么加验证强度):
- L0 单元/集成测试+审查(基线) / **L1 属性/模糊测试(默认启用)** / L2 变异测试(按需) / **L3 红队+E2E(可选)** / L4 形式化验证+灰度(仅核心)

**保证度三因子(乘法,任一为0则全盘0)**:
> 保证度 = 完备性 × 不可绕过 × 网自验
- 完备性(覆盖全不全)× 不可绕过(能不能跳过,本地hook可绕→远端CI→分支保护)× 网自验(非伪造oracle,不信模型声称)
- **乘法不是加法**:完备性0.9但不可绕过0(全绕)→实际0。先算三因子定位最弱,再用L0-L4针对性补。

## 9. 阶段化落地(从最小团队起步)

```
阶段0  人+单智能体,跑通核心管道,沉淀第一版事实来源文档
        (0.0 规格化生产:人按 prd-template/interaction-spec-template 写 PRD+交互规约)
阶段1  +测试+审查      ← 逻辑复杂时最先加,建立客观验证回路
阶段2  +架构师+知识管理者 ← 代码量增长时加,上治理和记忆
阶段3  +编排者+需求分析师 ← 任务变多需调度时加,全8核心角色到位(规格化归 01/06/design)
阶段4  按需加 红队/调试专家/DevOps
```
每阶段问:**当前最大瓶颈或最近失败,是不是因为缺某个角色?** 是→加;不是→别加。

## 10. 六条铁律

1. **先读后做**——动手前先读事实来源文档对应区块
2. **验证而非信任**——任何"完成了"必须有客观信号证明
3. **更新才算交付**——产出后必须更新文档对应区块
4. **需求结构化(按优先级分层)**——P0缺字段不准进下游;**UI触及的P0须标 `界面交互:是` + 交互规约章节**(对应 `docs/INTERACTION_SPEC.md`),guard-check 检查7 卡空值;**每条 P0 须列假设(带 已验证/未验证),检查8 卡;问题陈述+成功指标经多角色评审(04/05/design 提疑问)+06综合审+早期人 gate 确认才准规格化(治"解决错问题")**。模糊从源头放大10倍
5. **任何变更:改前评估影响 + 改后查逻辑错误**——改已交付的不评估=定时炸弹;改完不复查=盲区留到运行时
6. **可靠性维度(稳定可靠的硬维度)**——代码不只功能对,须过 性能/容错/安全/可观测/并发 5 维(04 写·03 架构·05 测·06 第10条审);PRD §5 非功能须可度量(01 预检⑥),否则 05 测不了。缺一即脆

## 一句话总结这条"可靠稳定"主线

> **事实来源文档**(共同记忆)→ **10角色目标对立**(多样性)→ **规格化(问题空间→早期人gate确认"我要"→产PRD+交互规约→freeze)+ 双层循环+星型隔离**(流程)→ **三基石安全系统**(防幻觉发现纠正 / 防失控撞墙叫人 / 异常处理按画像分流)→ **退出门禁(门禁0一致性+1-4客观+5人验收)**(交付权在人)。其中**异常处理+任务画像**是按场景分流的关键一环:让限制和失败handler从"一刀切常量"变成"按场景分流",并把最危险的**P4副作用型**用脚本卡死"绝不自动重试";**规格化阶段**补上流程最前端(问题空间→早期人gate确认"我要"→假设清单),让 UI 交互既有规约可依、又有断言可验(§6→V-UI-STRUCT)、还有门禁0卡一致性;**前端工作流**治"解决错问题"(B),让"做出来不是我要的"有可回溯痕迹。
