# 全局免疫记忆 (Immune Memory) —— 示例文件

> **跨项目共享的"已确认非 bug 清单"+"模型 × 任务适配档案"**。
> 每次审查前注入到 prompt 头部，避免模型把业务需求误判为 bug，避免不同项目重复踩坑。
>
> 借鉴 Onklaud 5 immune memory 思路：让审查越审越准、不重复报已确认的"假缺陷"。
>
> 维护者：审查者每轮发现"模型误判为 bug 但实际是业务需求"的项，追加到对应分类；
> 发现"模型 × 任务适配错配"的项，追加到第五节"模型 × 任务适配档案"。

---

## 使用方式

审查引擎调用时传 `immune_memory` 参数（本文件内容或子集），
prompt 会前置注入【已确认非 bug 清单】，模型审查时直接标 `confirmed_requirement`。

```python
from review_engine import council_review

immune = open("immune_memory.md").read()  # 路径按你的部署调整

council_review(
    code=...,
    immune_memory=immune,  # ← 注入
    ...
)
```

## 一、跨项目通用（所有项目共享）

### 通用误判模式

| 误导信号 | 伪「缺陷」 | 真实原因 |
|---------|-----------|---------|
| NaN 不显式处理 | `f64` 比较不检查 NaN | Rust 中 NaN 比较返回 false 是标准行为；如果业务接受 NaN=不通过，是合理的 |
| `.unwrap_or_default()` 静默吞错 | JSON 解析失败返回空 Vec | 业务允许：解析失败==无数据，下游已处理空值 |
| 字符串做枚举键 | 用 `String` 而非 `enum` | 一人维护项目，依赖最小化；枚举增加复杂度不值得 |
| 失败不自动重试 | 发布类操作失败不重试 | **防双写/防重复**——自动重试会导致重复创建 |
| `Mutex::lock().unwrap()` | 不处理中毒 | 业务可接受：Mutex 中毒=线程 panic，整个进程就该挂 |
| 测试硬编码绝对路径 | `TEST_DB_PATH = "<绝对路径>"` | 一人开发机，CI 不存在；不是 bug 是技术债 |

### 通用业务设计

- **幂等性优先**：纯函数 + 同输入同输出是设计目标，不是"巧合正确"
- **依赖最小化**：标准库够用就不引第三方 crate
- **错误降级而非崩溃**：单条数据解析失败→跳过，不 panic 整个管线
- **门禁由离线验证兜底**：模型说"通过"不算数，`cargo test`/`npm test`/`vite build` 真跑过才算

## 五、模型 × 任务适配档案 ★分派前必查

> **分派任何 LLM 任务前先查此表**——不是事后撞墙才发现模型不匹配。
> 探测方法：真实任务 probe（不设 max_tokens），记录输出上限/耗时/行为。
> ⚠️ 下表为示例数据（特定模型版本实测）；**模型升级后必须复测**，旧数据不能直接沿用。

### 5.1 模型真实上限（probe 实测示例）

| 模型 | 真实输出上限（不设 max_tokens） | 适合任务类型 | 不适合任务类型 | 备注 |
|------|----------------------------|-------------|--------------|------|
| **kimi-k2.7-code** | 29064 tokens 稳定 | 逐行找 bug / 代码审查 / 找 typo / 找隐藏逻辑缺陷 | 轻量确认类任务 / 快响应任务 | 思考型模型，reasoning_tokens 占 80%；轻量任务不需要深思考，反而吃满配额空回复 |
| **deepseek-v4-pro** | 29035 tokens 稳定 | 架构审查 / 系统设计层 / 找 panic 路径 / 浮点比较 | 轻量对照确认（思考太深，太慢） | 思考型模型；max_tokens=3000 时 reasoning 吃满正文 0 字符空回复 |
| **deepseek-v4-flash** | 29422 tokens 稳定 | 对照列表确认 / 文本蒸馏 / 结构化抽取 / 快响应任务 | 逐行找 bug / 深度架构审查 | 快响应，结构化抽取类任务足够 |
| **qwen3.8-max** | 待复测（3.7 实测 4506 tokens 任务自停） | 仲裁 / 综合裁决 / 合并分歧 | 逐行代码审查 / 长输出任务 | 思考型模型；max_tokens 策略同族（设小值空回复，不设正常） |
| **glm-5.2** | PONG 正常 | 日常主用 / 编排者 / 角色对话 | 小 max_tokens 任务——思考型同病 | 不用于审查（审查走异架构双模型） |

### 5.2 任务 × 模型匹配矩阵

| 任务类型 | 推荐主用模型 | 不推荐 | 理由 |
|---------|------------|--------|------|
| **代码逐行审查（找 bug）** | kimi-k2.7-code | flash 类 | 思考型擅长逐行深挖；快模型漏细节 |
| **架构审查（系统设计层）** | deepseek-v4-pro | flash 类 | pro 擅长设计层；flash 漏深度问题 |
| **仲裁（合并分歧）** | qwen3.8-max | kimi/deepseek | 综合裁决视角；已参与审查的模型有立场偏 |
| **delta_review（对照列表确认）** | deepseek-v4-flash 类 | kimi | 轻量确认任务；思考太猛吃满 max_tokens 空回复 |
| **文本蒸馏（结构化抽取）** | flash 类 | pro | 快 10 倍+，结构化抽取足够 |
| **PONG 探活** | 任意（max_tokens=10 固定） | — | 非思考任务不会触发 reasoning 吃满 |

### 5.3 max_tokens 配置策略

**核心结论**：**不设 max_tokens 字段，让模型用自己默认上限**。

| 策略 | 结果 | 结论 |
|------|------|------|
| 不设 max_tokens | 思考型模型稳定输出其真实上限 | ✅ 最佳 |
| 设小值（如 3000） | reasoning_tokens 吃满配额，正文 0 字符空回复 | ❌ 最差——伪上限 |
| 设过大值 | 部分模型超过真实上限反而崩塌 | ❌ 不是越大越好 |

**根因**：思考型模型的 reasoning_tokens 不挤占正文配额时正常工作；显式设 max_tokens 反而限制 reasoning 导致"思考不完就停"。

### 5.4 已踩过的模型适配错配（防复发）

| 错配 | 真相 | 纠正 |
|------|------|------|
| 轻量确认任务用深度思考模型 | 思考太猛吃满配额空回复 | 轻量任务用 flash 类快模型 |
| 全局 max_tokens=3000 | 思考型 reasoning 吃满配额正文 0 字符 | 删除所有 max_tokens 字段 |
| 全局 max_tokens=32000 | 超真实上限反而崩 | 不设才是真默认上限 |
| 蒸馏任务用 pro 级模型 | 太慢（10 倍+），能力过剩 | 用 flash 类 |
| 代码里硬编 max_tokens | 换个模型就复发 | 必须读全局配置 |
